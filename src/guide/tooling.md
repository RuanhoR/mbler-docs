# Recommended Tooling: ESLint, Vitest and the MFD Download Page

A project generated by `create-mbler` ships with build, watch and type checking out of the box. This page introduces three recommended companion tools — **ESLint** (linting), **Vitest** (unit testing) and **MFD** (a static download page) — each with a complete from-zero setup. Everything here comes from a real, actively maintained project, [LuckBlock](https://github.com/RuanhoR/LuckBlock), so you can copy it verbatim and reproduce it.

You do not need to be a toolchain developer; if you can use a terminal, you are set. The three tools are independent — pick the ones you need.

## Conventions

Run all commands in your project root (the directory containing `mbler.config.js`). pnpm is used in the examples — npm users can substitute `pnpm add -D` with `npm i -D`.

## ESLint: lint your TS and .mcx code

ESLint covers two kinds of checks: general rules for TypeScript sources, and structural validation of `.mcx` files (event bindings, duplicate tags, and so on).

### Install

```bash
pnpm add -D eslint @typescript-eslint/eslint-plugin @typescript-eslint/parser @mbler/eslint-plugin-mcx
```

### Configuration

Create `eslint.config.mjs` in the project root (flat config):

```js
// @ts-check
import tseslint from "@typescript-eslint/eslint-plugin";
import tsparser from "@typescript-eslint/parser";
import mcx from "@mbler/eslint-plugin-mcx";

export default [
  {
    // build output and dependencies are not linted
    ignores: ["dist/**", "node_modules/**", "dist.mcaddon"],
  },
  {
    // general rules for TypeScript sources and tests
    files: ["behavior/scripts/**/*.ts", "tests/**/*.ts"],
    languageOptions: {
      parser: tsparser,
      ecmaVersion: "latest",
      sourceType: "module",
    },
    plugins: {
      "@typescript-eslint": tseslint,
    },
    rules: {
      "@typescript-eslint/no-explicit-any": "error",
      "prefer-const": "error",
      "no-undef": "off",
      "no-unused-vars": "off",
      "no-empty": "off",
    },
  },
  // lint .mcx files (template + embedded <script>); recommended rules included
  mcx.configs.recommended,
];
```

### Wire up scripts

Add to the `scripts` section of `package.json`:

```json
{
  "scripts": {
    "lint": "eslint .",
    "lint:fix": "eslint . --fix"
  }
}
```

```bash
pnpm lint        # check
pnpm lint:fix    # auto-fix what can be fixed
```

For the individual rules in `mcx.configs.recommended` (such as "the bound event name must exist in `@minecraft/server`"), see the rule table in the [ESLint & Vitest Plugins](./plugins) page. Rules read the `@minecraft/server` type definitions installed in your project, so there is no event list to maintain by hand.

## Vitest: unit tests without launching the game

Addon scripts depend on `@minecraft/server`, which is **only available inside the game** — even when installed from npm, it cannot load under Node. The fix is to alias it to a local mock in the test config: tests only need the import-time surface to exist, so the mock does not have to reproduce game behavior.

### Install

```bash
pnpm add -D vitest
```

### Mock and configuration

Create `tests/mocks/minecraft-server.ts` with a minimal stub (add or remove exports to match what your project imports):

```ts
// tests/mocks/minecraft-server.ts
// Minimal @minecraft/server(+ui) stub for unit tests under Node:
// imports must resolve, game behavior is not simulated.
export const world = {
  getDimension: () => {
    throw new Error("not available outside Minecraft");
  },
  sendMessage: () => {},
};
export const system = { run: (fn: () => void) => fn() };
export const BlockComponentTypes = {};

export class ItemStack {
  constructor(
    public _id?: string,
    public _amount?: number,
  ) {}
}
export class Block {}
export class Player {}
export const EquipmentSlot = { Mainhand: "Mainhand", Offhand: "Offhand" };
export const EntityComponentTypes = {};
export const EnchantmentType = {};
```

Create `vitest.config.ts` in the project root:

```ts
import * as path from "node:path";
import { fileURLToPath } from "node:url";
import ts from "typescript";
import { defineConfig } from "vitest/config";
import { vitePlugin } from "@mbler/mcx-core";

const __dirname = path.dirname(fileURLToPath(import.meta.url));
const serverMock = path.join(__dirname, "tests", "mocks", "minecraft-server.ts");

export default defineConfig({
  resolve: {
    alias: {
      // beta runtime packages cannot load under Node; unit tests only need
      // the import-time surface to exist
      "@minecraft/server": serverMock,
      "@minecraft/server-ui": serverMock,
    },
  },
  plugins: [
    vitePlugin(
      {
        // bare ids (e.g. @mbler/mcx injected by compiled .mcx) resolve here
        moduleDir: path.join(__dirname, "node_modules"),
        tsconfigPath: path.join(__dirname, "tsconfig.json"),
        sourcemap: false,
        ts,
      },
      // throwaway output dirs; tests never read them
      {
        dist: path.join(__dirname, ".mcx-out"),
        behavior: path.join(__dirname, ".mcx-out"),
        resources: path.join(__dirname, ".mcx-out"),
      },
    ),
  ],
  test: {
    include: ["tests/**/*.spec.ts"],
    environment: "node",
  },
});
```

`vitePlugin` comes from `@mbler/mcx-core` (already a dependency of mcx projects generated by `create-mbler`); it lets test code `import` the compiled form of `.mcx` files directly.

### Writing and running tests

Tests live in `tests/` and are named `*.spec.ts`. A minimal example:

```ts
// tests/core.spec.ts
import { describe, expect, it } from "vitest";
import { randomNum } from "../behavior/scripts/core/utils";

describe("randomNum", () => {
  it("stays within [min, max]", () => {
    for (let i = 0; i < 200; i++) {
      const n = randomNum(3, 7);
      expect(n).toBeGreaterThanOrEqual(3);
      expect(n).toBeLessThanOrEqual(7);
    }
    expect(randomNum(5, 5)).toBe(5);
  });
});
```

Wire up the script and run:

```json
{
  "scripts": {
    "test": "vitest run"
  }
}
```

```bash
pnpm test
```

::: tip What is worth testing
Pure logic functions (randomness, parsing, numeric work, data transforms) are ideal for unit tests; anything that touches the game runtime (world events, entity manipulation) can only be tested at import time under the mock. LuckBlock's practice: full coverage for utilities and parsers, game interaction verified manually in-game.
:::

## MFD: generate a download page for your addon

Finished addons need distribution. MFD (`@mbler/mfd`) generates a **static download page** for your addon — a markdown introduction, an MC version selector, and a `.mcaddon` download link. The output is a plain static directory you can host anywhere (GitHub Pages, Cloudflare Pages, …) with no registry involved.

### Install and configure

```bash
pnpm add -D @mbler/mfd
```

Create `mfd.config.js` in the project root:

```js
// @ts-check
import { defineConfig } from "@mbler/mfd";

export default defineConfig({
  title: { zh: "幸运方块", en: "Lucky Block" },
  mcVersion: { min: "1.26.30", max: "1.26.45" },
  description: {
    zh: `# Lucky Block

A simple Minecraft Bedrock **Lucky Block** gameplay addon.

## Install

Download the \`dist.mcaddon\` matching your Minecraft version and import it into the game.
`,
    en: `# Lucky Block

A simple Minecraft Bedrock **Lucky Block** gameplay addon.

## Install

Download the \`dist.mcaddon\` matching your Minecraft version and import it into the game.
`,
  },
});
```

- `title` / `description` support both languages; the page language follows the visitor's system language;
- `mcVersion` min/max drives the range of the version selector on the page;
- `description` is full markdown, rendered as-is.

### Build the page

First make sure `mbler build` has produced `dist.mcaddon` in the project root (release build: `cross-env BUILD_MODULE=release mbler build`), then:

```bash
npx mfd page
```

The output lands in `dist-page/<slug>/` (the slug is derived from the addon name) as plain static files (`index.html`, `assets/`). Upload the directory as-is to any static host; once `dist.mcaddon` is deployed alongside the page, the download link points at it automatically.

Local preview:

```bash
npx mfd serve
```

This starts a local server serving the page, manifest and addon endpoints — open the printed address in a browser.

## Putting it all together: recommended scripts

With all three tools configured, the `scripts` section of `package.json` looks like this (identical to LuckBlock's):

```json
{
  "scripts": {
    "dev": "mbler watch",
    "build": "cross-env BUILD_MODULE=release mbler build",
    "dev-build": "mbler build",
    "type-check": "mcx-tsc",
    "lint": "eslint .",
    "lint:fix": "eslint . --fix",
    "test": "vitest run"
  }
}
```

The after-coding verification loop:

```bash
pnpm type-check && pnpm lint && pnpm test && pnpm build
```

When releasing, add one more step — `npx mfd page` — to refresh the download page. None of these commands require launching the game.
